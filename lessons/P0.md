# P0 — The foundation

## TLDR

Before Craton learns anything about the Earth, it needs a building site that can't collapse.
P0 builds an empty project with one rule baked into the machinery: **it can only get better.**
One command, `craton check`, refuses any change that breaks a test, edits history, fakes a number,
or makes a benchmark worse. There's no model yet, and that's the point.

## The idea, step by step

**1. Why start with nothing?** Picture building a tower and discovering at floor 9 that the foundation
was poured wrong. You don't fix floor 9. You knock the tower down. Research code dies this way all the
time: someone tweaks a dataset, a test quietly changes, a number in a table was typed by hand, and six
months later nobody can tell whether the model improved or the exam got easier.

**2. So the foundation is made of refusals.** Everything in P0 is a machine that says *no*:

| It refuses | So that |
|---|---|
| code that fails lint, types or tests | a change can't silently break another part |
| a `SCOREBOARD.md` that differs from what the JSON renders to | no number is ever typed by hand |
| an edited old line in `LOGBOOK.md` or `DECISIONS.md` | history is only ever added to |
| a benchmark run that is worse than the best one ever recorded | progress is real, never luck |
| a config whose shape doesn't match its claimed size | "mini" can't quietly outgrow the laptop |

**3. The ratchet.** A ratchet is the wrench that only turns one way. Every benchmark task has a
*champion*: its best accepted score. A new run is compared with the champion, task by task:

- better by more than the noise → **improved**, it becomes the new champion
- worse by more than the noise → **regressed**, the run is refused
- in between → **same**, accepted, but the champion stays

Why not just compare with the previous run? Because then you could lose a hair every time, each loss
"within noise", and after a hundred runs you've lost a lot. Comparing with the champion makes that
impossible.

**4. What is "noise"?** Train the same model with three different random seeds and you get three slightly
different scores. That spread is luck, and the standard deviation measures it. Craton calls a difference
real only if it's bigger than **two standard deviations**, using whichever side was noisier. With three
seeds, that's a deliberately strict bar.

**5. Seeds.** A computer's "random" numbers come from a formula that starts from a seed. Same seed, same
numbers, every time. `seed_everything(7)` sets the seed for Python, NumPy and PyTorch at once, and switches
the GPU to its deterministic algorithms, so a run can be repeated exactly. `derive_seed(0, "ensemble", 3)`
makes a separate, stable seed for ensemble member 3, so members don't share randomness by accident.

**6. Precision and the RTX 2060.** Numbers on a GPU can be stored in 32 bits (fp32) or 16 bits (fp16, bf16).
Sixteen bits is twice as fast and half the memory, which matters a lot on a 6 GB card. The catch: fp16 can't
represent very small numbers, so tiny gradients round to zero and training stalls. The fix is a **gradient
scaler**: multiply the loss by a big number before backpropagation, divide the gradients back afterwards.
bf16 avoids the problem with a wider range, but needs an Ampere GPU or newer. The 2060 is Turing, one
generation earlier. So Craton plans precision per machine: a config may *ask* for bf16, and on Turing it
gets fp16 with a scaler, plus a warning.

**7. Parameters, honestly counted.** A transformer layer of width *d* has four *d × d* attention matrices
and a feed-forward block of *d × 4d* and *4d × d*. That's 4d² + 8d² = **12 d²** weights per layer, plus small
change for biases and norms. Mini has d = 256 and 6 layers: 12 × 256² × 6 ≈ 4.7 million. GPT-2 small has
d = 768 and 12 layers: ≈ 85 million. Each config states its range, and loading it fails if the arithmetic
disagrees.

## The LLM analogy

Every serious LLM lab builds the training-infrastructure repo before the first run: configs, seeding,
logging, an evaluation harness, CI. Nobody remembers that part of the story, but it's why their numbers
can be trusted. The ratchet is Craton's version of "don't merge if the evals drop".

Where the analogy breaks: LLM evals are cheap to add and change all the time. Craton's benchmarks are
frozen forever (each task carries a fingerprint of its test data), because in geology the test sets are
rare real events, like the 2016 Amatrice–Norcia sequence. You can't make another one.

## What the code does

In the order a check flows:

1. `craton/cli.py` — the `craton` command. `check` runs every step and prints a ✓ or ✗ for each.
2. `craton/config.py` — loads `configs/*.yaml` into strict models; unknown keys are errors; `trunk_params`
   is the 12 d² rule with the biases included.
3. `craton/hardware.py` — `probe()` asks PyTorch (or `nvidia-smi`) what GPU this is; `plan_precision()` turns
   a requested precision into what actually runs; `smoke_test()` trains a tiny network to prove it.
4. `craton/seed.py` — `seed_everything`, `derive_seed`, `rng`.
5. `craton/bench/results.py` — the shape of a benchmark run (scores per seed, per task, with fingerprints)
   and of the scoreboard (champions + history).
6. `craton/bench/ratchet.py` — `judge()` gives every task a verdict; `accept()` folds a passing run in.
7. `craton/bench/scoreboard.py` — renders `SCOREBOARD.md` from the JSON, and checks they still agree.
8. `craton/records.py` — compares `LOGBOOK.md` and `DECISIONS.md` with git, line by line.

## The numbers

None on the scoreboard yet, by design. The first scores are simple baselines in P3, measured before any
model exists.

Two numbers did come out of P0, from the laptop it was built on:

- `craton config mini`: **4,739,072** trunk parameters.
- `craton doctor --smoke`: 60 fp16 steps with gradient scaling on the RTX 2060, loss **0.522 → 0.001**,
  peak **17 MiB** of VRAM. The mixed-precision path works end to end.

## Try it yourself

```console
uv run craton doctor --smoke          # what your machine can run, proven with a real training step
uv run craton config regional         # 85M parameters: check the 12·d² arithmetic by hand
```

Then try to cheat. Open `SCOREBOARD.md`, change any character, and run `uv run craton check`. It fails, and
tells you to regenerate the file. Undo it with `uv run craton scoreboard`.

## Check yourself

<details><summary>1. A run scores 3.05 ± 0.05 on a task whose champion is 3.00 ± 0.10 (lower is better). Accepted?</summary>

Noise = 2 × max(0.10, 0.05) = 0.20. It's worse by 0.05, which is within noise: verdict **same**. Accepted,
and the champion stays at 3.00.
</details>

<details><summary>2. Why does every score need at least three seeds?</summary>

With one seed there's no spread to measure, so you can't tell skill from luck. Two seeds give a very shaky
standard deviation. Three is the smallest number that gives a usable estimate without tripling the cost
too much.
</details>

<details><summary>3. A config asks for bf16 on an RTX 2060. What runs?</summary>

fp16 with a gradient scaler, plus a warning. Turing has no native bf16.
</details>

<details><summary>4. Why compare a run with the champion and not with the previous run?</summary>

Small within-noise losses would stack up run after run. Against the champion, they can't.
</details>

<details><summary>5. You find a typo in an old DECISIONS.md entry. What do you do?</summary>

Leave it. Add a new entry that corrects it. The record is append-only; the check refuses edits.
</details>

## Glossary

- **Ratchet** — the rule that a change lands only if no benchmark gets worse beyond noise.
- **Champion** — a task's best accepted score.
- **Seed** — the starting number of a random number generator; same seed, same sequence.
- **fp16 / bf16 / fp32** — 16-bit (narrow range), 16-bit (wide range, Ampere+), 32-bit floating point.
- **Gradient scaler** — multiplies the loss so small fp16 gradients don't round to zero.
- **Fingerprint** — a hash of a task's test data and metric; if it changes, it's a different task.
- **Append-only** — you may add lines, never change or delete old ones.
- **CI** — continuous integration: a server runs `craton check` on every change.
